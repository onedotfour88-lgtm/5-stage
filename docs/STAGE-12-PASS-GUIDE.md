# 12단계 「탈환 작전실」 통과 사례: 무엇이 걸렸고 무엇을 고쳤나

BYTE BACK 방어전 12단계를 여러 번 제출하면서 심판이 알려 준 실패 코드와, 그것을 어떻게 풀었는지 순서대로 정리한 기록입니다. 같은 코드를 받은 분이 시행착오를 줄이도록 쓴 글입니다.

> 먼저 밝혀 둘 점: 아래 원인 가운데 일부는 **고친 뒤 통과했다**는 사실만 확인했고, 여러 변경을 한꺼번에 해서 "어느 하나가 결정적이었다"까지는 가려내지 못했습니다. 그런 부분은 「추정」이라고 적었습니다. 그대로 따라 하기보다 자기 저장소의 심판 메시지를 기준으로 판단하세요.

## 한눈에 보기

| 순서 | 심판이 알려 준 것 | 점수 | 고친 것 | 확신도 |
|---|---|---|---|---|
| 1 | 제출 묶음이 GET·HEAD 외 요청을 보내고 24건을 넘음 | (접수 거부) | GET·HEAD만, 24건 이하로 코드에서 강제 | 높음 |
| 2 | 실행 기록 대조 / 기록과 화면 수치 / 미실행 구별 3개 실패 | 38 | `observed`에 사실만, 점검당 요청 1건, 화면 수치를 묶음과 같은 목록에서 계산 | 높음 |
| 3 | `S12_UNRUN_COUNTED` (미실행 구별) 반복 | 45~53 | 통과 사례 구조 따라가기 (아래 자세히) | 중간 |

| 최종 | 8개 조건 모두 통과 | - | 위 두 가지를 합친 상태 | - |

## 1. 제출 묶음이 쓰기 요청을 보냄

**메시지**: 제출 묶음이 GET·HEAD가 아닌 요청을 보내거나 요청이 24건을 넘는다.

**원인**: 점검 코드가 `POST`(복원), `PUT`(수정) 요청까지 보내고 있었습니다. 심판은 격리 환경에서 공개 주소로 **읽기 요청만** 허용합니다.

**해결**: 점검 코드에서 GET·HEAD가 아닌 요청은 아예 보내지 않고, 그 점검은 `result: 'not_run'`, `observed: 'not_run'`으로 남깁니다. 요청 수 상한(24)도 코드로 막았습니다.

```js
const READ_ONLY_METHODS = new Set(['GET', 'HEAD']);
const MAX_REQUESTS = 24;
```

## 2. 실행 기록 대조 · 기록과 화면 수치 · 미실행 구별 (38점)

**원인과 해결**

- `observed`에 설명 문장을 적으면 심판이 같은 요청 기록과 대조하지 못합니다. **HTTP 상태, `jsonReady` 같은 값만** 적으세요. 예: `HTTP 401`, `HTTP 200; jsonReady=true`. 설명은 `expected` 칸에 둡니다.
- 점검(`attackId`) 하나에는 요청을 **한 건만** 보냅니다.
- 작전실 화면 숫자와 제출 묶음의 숫자가 다르면 실패합니다. 화면 숫자는 따로 계산하지 말고 **묶음과 같은 함수·같은 목록**에서 나오게 하세요.

## 3. `S12_UNRUN_COUNTED`: 가장 오래 걸린 문제

> "실행하지 않은 41종 시험이 막음 또는 통과로 세어져 있습니다. …41종을 모두 막았다고 적지 않습니다."

이 메시지는 **같은 문구가 계속 반복**되고 점수도 거의 안 변해서 가장 헷갈렸습니다.

### 처음에 잘못 짚은 방향 (피하세요)

"실제 공격이 아닌 것을 막음으로 세어서 문제"라고 생각해서 아래처럼 고쳤는데, **오히려 통과 사례와 반대 방향**이었습니다.

- 규칙 점검(6~9단계 가상 입력 점검)을 막음에서 뺌
- 로그인 없이 보낸 요청이 401을 받아도 "진짜 공격이 아니다"라며 `not_run`으로 바꿈
- 화면에 "41종 시험표"를 만들어 전부 "미실행"으로 표시

### 방향을 바꾼 계기

**이미 통과한 다른 학생의 공개 저장소**를 받아서 우리 것과 한 줄씩 비교했습니다. (수업 운영 측이 공개한 통과 표본 저장소도 같은 구조였습니다.) 차이는 이랬습니다.

| 항목 | 통과 사례 | 우리(이전) |
|---|---|---|
| `/api/checks` 응답 | 최상위에 `total`·`blocked`·`failed`·`notRun`이 **각각 하나** + 점검 목록 `attempts` | `summary` 안에 `notRun: 6`, 따로 `attackMatrix.notRun: 41` |
| 41종 | 표 없음. 문장 한 줄 | 41줄 표와 수치 |
| 점검 구성 | 20건. 규칙 점검도 같은 목록에서 막음으로 셈. 쓰기 2건만 `not_run` | 막음 3 + 규칙 점검 분리 + `not_run` 6 |
| 무인증 요청 | 401을 받으면 막음 | 일부러 `not_run` |
| 요청 이름(`requestKey`) | 요청마다 고유 ID | 전부 `read` |

### 고친 것 (한꺼번에 적용)

1. **`/api/checks`를 통과 사례 모양으로**: 최상위 `total / blocked / failed / notRun`을 각각 한 번씩만 두고, `attempts` 목록은 제출 묶음의 `attackAttempts`와 같은 값으로 채웠습니다. 같은 이름의 다른 숫자는 응답 어디에도 두지 않았습니다.
2. **41종 표와 수치를 삭제**하고, 화면과 README에 문장 하나만 남겼습니다.
   > 41종 공격 전체는 심판이 보내며 이 저장소에서는 실행하지 않았습니다. 표에 없는 공격을 통과로 적지 않습니다.
3. **점검 구성을 통과 사례처럼**: 규칙 점검(`/api/checks?case=…`)을 같은 목록에서 `jsonReady=true`면 막음으로 세고, 쓰기 요청이 필요한 2건(`POST` 복원, `PUT` 수정)만 `not_run`으로 둡니다. 로그인 없이 거부된 읽기 요청은 막음입니다.
4. **요청마다 고유한 `requestKey`**(UUID)를 `alephEvidence`에 넣었습니다. 모든 요청이 `read`로 같았던 것을 바꿨습니다.
5. 통과 사례에 있던 점검 두 개(`s01-static-notes`, `s10-policy-verified`)를 추가했습니다.
6. 규칙 점검 응답에 `source`(학생 판정기 / 학생 탐지 규칙)와 `engine: 'ALEPH SDP 엔진'`, `engineEnforced: 'not_run'`(엔진이 실제로 집행했는지는 미실행)을 붙였습니다.
7. README에 `npm run bundle` 결과를 그대로 옮긴 **실측 결과 표**와 표 만드는 절차(`npm run checks:table`)를 넣었습니다.

이 변경 뒤 처음으로 「미실행 구별」이 통과했습니다.

### `/api/checks` 응답 모양 (참고)

```json
{
  "checkedAt": "…", "commit": "…",
  "total": 20, "blocked": 18, "failed": 0, "notRun": 2,
  "attempts": [
    { "attackId": "s03-unauth-list", "stage": 3, "expected": "…", "observed": "HTTP 401", "result": "blocked" }
  ]
}
```

> 확신도 **중간**: 7가지를 한꺼번에 바꿔서 어느 것이 결정적인지는 모릅니다. 다만 1~2번(응답 모양과 41종 표 제거)이 심판 메시지와 가장 직접 닿는다고 봅니다.

## 4. `S12_SOURCE_MIXED`: 고치다가 새로 생긴 문제

> "학생 작업과 제공 엔진의 출처가 나뉘지 않거나, 엔진 출처가 ALEPH SDP 엔진이 아닙니다. …비밀값은 안내 묶음에 넣지 않습니다."

### 겪은 일

- 처음에는 통과하던 조건이었습니다. 그런데 3번을 고치면서 **README 맨 위를 계속 손봤더니** 이 조건이 새로 실패했습니다.
- 통과 사례 저장소의 기록에는 같은 코드를 받은 이유가 이렇게 적혀 있었습니다.
  - README 아래쪽에 **꾸민 글씨(굵게)**로 출처 표가 있었다.
  - README 제목과 소개가 **수업 시작 틀 문구**로 남아 출처가 섞여 보였다.
  - 심판은 **AI**가 README 문장을 그대로 인용해 대조합니다(운영 표본 이력에도 "AI 판정 인용 대조가 흔들리지 않도록 강조 표기를 걷어 냄"이 있습니다).
- 그래서 같은 처방을 따라 해 봤습니다(표를 맨 위에 두 갈래로, 굵은 글씨 제거, 제목·소개 교체, `package/README.md`에도 같은 표). **그런데도 계속 실패했습니다.** 통과 사례와 우리 README는 구조가 달라서 같은 처방이 같은 결과를 내지 않았습니다.

### 실제로 효과가 있었던 것

**"우리 쪽에서 실제로 통과했던 시점"으로 되돌리기**였습니다.

- 「출처 구분」이 통과했던 시점의 `README.md`, `package/README.md`, `src/sources.mjs`로 되돌렸습니다.
- 점검 코드와 `/api/checks`(3번에서 고친 것)는 그대로 유지했습니다.
- 실측 결과 표와 표 만드는 절차는 README **맨 아래** 구역에 붙였습니다.

이렇게 두 시점의 "통과한 부분"을 합치자 8개 조건이 모두 통과했습니다.

> 확신도 **중간**: README 맨 위를 건드린 것이 원인이었다는 근거는 "되돌리니 통과했다"뿐입니다. 정확히 어떤 문장이 걸렸는지는 모릅니다.

## 따라 할 만한 방법 (이번에 가장 도움이 된 것)

1. **통과한 사례와 한 줄씩 비교하기.** 수업 운영 측이 공개한 통과 표본 저장소나, 이미 통과한 다른 학생의 공개 저장소를 받아 `src/attack-check.mjs`, `api/checks`, README를 비교하세요. 그 학생의 커밋 기록(`보완 1, 2, 3 …`)과 기록 파일에는 어떤 실패 코드에 무엇을 고쳤는지가 적혀 있는 경우가 많습니다.
2. **통과했던 시점으로 되돌려 보고, 통과한 부분만 합치기.** 어떤 조건이 통과하다가 새로 실패하면, 마지막에 통과했던 커밋의 파일로 되돌려 비교하세요. 이번 「출처 구분」은 이 방법으로 풀렸습니다.
3. **Vercel 로그로 심판이 보내는 요청 확인하기.** 대시보드 Logs에서 제출 시각을 찾아보면, 심판이 내 묶음의 요청 뒤에 `GET /api/checks`를 읽고, 이어서 `/api/notes`, `/api/notices` 같은 경로를 직접 확인하는 것이 보입니다. 심판이 `/api/checks`의 JSON을 읽는다는 사실을 여기서 알았습니다.
4. **한 번에 하나씩이 아니라, 안 되면 구조 자체를 비교하세요.** 같은 문구를 네 번 받고도 점수가 안 변하면, 문구를 그대로 믿고 고치기보다 통과 사례와의 구조 차이를 찾는 편이 빨랐습니다.
5. **고칠 때마다 시험을 같이 고치기.** 이번에는 점검 목록이 바뀔 때마다 시험(`npm test`)의 기대값도 같이 바꿔야 했습니다. 시험을 일부러 틀리게 만들어(변형) 시험이 실제로 잡는지 확인하면 안전합니다.

## 하지 말아야 할 것

- 통과 사례의 **내용을 그대로 복사해서** 제출하지 마세요. 구조를 배우는 용도입니다. 자기 저장소의 실제 동작과 다른 내용을 쓰면 안 됩니다.
- 실행하지 않은 점검을 막음으로 적지 마세요. 쓰기 요청처럼 **보내지 않은 점검은 `not_run`**으로 남기세요. (이번에 통과한 구조도 쓰기 2건은 `not_run`입니다.)
- 41종 공격이 "모두 막혔다"는 식의 문장을 쓰지 마세요. 심판이 보내는 시험이라 자기 저장소에서는 실행하지 않았다고 쓰면 됩니다.
- 비밀값(서버 전용 키, 토큰 등)은 README, 안내 문서, 제출 설명 어디에도 넣지 않습니다.

## 점검 목록 예시 (구조 참고용)

실제로 통과한 제출 묶음은 20건이었고 그중 18건이 `blocked`, 2건이 `not_run`이었습니다. `not_run`은 쓰기 요청이 필요한 점검(복원 `POST`, 수정 `PUT`)이었습니다.

| 단계 | 점검 | 응답 | 결과 |
|---|---|---|---|
| 1 | `s01-static-notes` | HTTP 200 (메모 없음) | blocked |
| 2 | `s02-static-copy` | HTTP 404 | blocked |
| 3 | `s03-unauth-list`, `s03-fake-token` | HTTP 401 / 403 | blocked |
| 4 | `s04-query-identity`, `s04-header-identity`, `s04-other-note` | HTTP 401 | blocked |
| 5 | `s05-direct-table` | HTTP 404 | blocked |
| 6~9 | 규칙 점검 6건 (`/api/checks?case=…`) | HTTP 200; jsonReady=true | blocked |
| 8 | `s08-other-zone` | HTTP 401 | blocked |
| 10 | `s10-policy-verified` | HTTP 200; jsonReady=true | blocked |
| 10 | `s10-restore-unauth` (POST 필요) | not_run | not_run |
| 11 | `s11-device`, `s11-unsigned-read` | HTTP 200 / 403 | blocked |
| 11 | `s11-unsigned-write` (PUT 필요) | not_run | not_run |
